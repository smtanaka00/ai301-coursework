# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity | The diff's full list of changed files and hunks, read against the plan's stated scope (in-scope list, not-in-scope/deferred items, and `## Deviations` notes). The PR description's own fidelity claims ("implements the plan," "no changes beyond X"), read against what the diff actually contains. | Pass if every changed file and hunk falls inside the plan's in-scope list, or is accounted for by an explicit `## Deviations` note explaining what changed and why, AND the description's fidelity claims match what the diff actually delivers (claims neither more nor less). An honestly noted deviation — scoping down, or a documented change of approach — is not a failure; it is the opposite of the failure this check catches. Fail if the diff contains a change the plan never named and no deviation note accounts for it (silent drift upward: an unrequested rewrite, a new config option, a refactor "while in there"), or if the description asserts fidelity ("exactly as planned," "no functional changes outside X") that the diff contradicts in either direction (more than claimed, or a promised piece quietly missing). Unclear only if the plan's scope section is itself too vague to compare the diff against. | required |
| Decisive test evidence | The `test_evidence.md`/test-evidence section's before-and-after output, read against the plan's test plan and the original repro steps it was built from. The repo's own required checks (`make test-unit`, `make test-integration`, `make lint`, `make typecheck`, or the package's named equivalent) and their reported results. | Pass if the evidence shows the specific observable artifact the test plan named, exercised on the actual bug path (not a control case or an unrelated path standing in for it), with a before state and an after state that differ the way the plan predicted, AND every one of the repo's named checks was run with its result reported honestly (a reported failure with a stated reason still counts as evidence; an omitted check does not). Fail if the evidence is a vague claim ("tests pass," "verified working," "tested locally") with no before/after shown, if the artifact exercised is a path the fix didn't touch (the control case, not the bug case), or if a required check was never run or its result never reported. Unclear only if the package gives genuinely no test-evidence section to read. | required |
| Reviewable diff | The unified diff itself, hunk by hunk, and the commit list/messages. | Pass if every hunk visibly serves the named fix and nothing else, and commit messages describe what each commit does. Fail if the diff carries debris: commented-out code, debug prints/`eprintln`/`console.log` left in, dead functions or unused variables kept "for reference," stray TODOs unrelated to the fix, pure formatting/re-indent churn, or an unrelated hunk folded in alongside the real change — regardless of how correct the core fix is. Commit messages like "wip," "fix," or "misc cleanup" are a signal to look harder at the diff for exactly this kind of debris, not a failure on their own. Unclear never applies here: the diff is always fully readable from the package or the branch. | required |
| Standards & disclosure | The repo's stated PR-template sections and the repo's own contribution/AI-use policy (from the repo-facts block, or live, the repo's `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the candidate PR's title, description, and any explicit maintainer direction already given in the thread. | Pass if every section the template requires has real, specific content (not a restated boilerplate placeholder or a blank checkbox left for the reviewer to fill), the issue is named (`Closes #<n>` or equivalent), and an AI-use disclosure is present wherever one is required — by the repo's own stated policy in eval mode, and always, regardless of what Path Review's own template says, in live mode, because the course requires disclosing AI assistance on every graded submission (the assignment's "Notes for Reviewers" is where it goes when the template carries no dedicated section). Also pass only if the description does not contradict explicit direction a maintainer already gave in the thread. Fail if a required template section is left as boilerplate or empty, the issue is never named, a required disclosure is absent, or the description ignores or contradicts explicit prior maintainer direction. | required |

## Verdict rule

Accept only if all four required checks pass. A fail on any single required check holds the package, no matter how strong the others are: a diff can be flawless and still hold for an unreported test, or fully tested and still hold for silently carrying an unplanned rewrite, or both of those and still hold for ignoring the repo's own template. There are no preferred checks this week; there is exactly one PR package to grade, not several to rank.

`unclear` on any required check counts as a fail for that check (and therefore forces reject): a PR whose fidelity, test evidence, diff cleanliness, or standards compliance this package cannot verify is not ready to submit.
