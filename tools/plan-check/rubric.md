# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis grounded | The plan's stated cause (its Diagnosis/Cause section), read against every data point in the repro evidence: each step, timing, and especially any control run or alternate-condition result that could rule a cause in or out. If the thread already names a confirmed cause, also read the stated cause against that. | Pass if every repro-evidence data point is either consistent with the stated cause, or explicitly addressed by a specific, mechanistic explanation in the plan that reconciles it (not a generic hand-wave). Fail only if a data point is left unaddressed and contradicts the stated cause, or the plan's explanation for an apparently-contradicting point is generic/hand-wavy with no stated mechanism. A plan that notices a data point that looks like it could cut against its own cause, and explains specifically why it doesn't, has done the grounding work this check rewards — do not fail it for the data point merely existing. Unclear only if the repro evidence genuinely contains nothing that bears on this specific cause either way. | required |
| Scope bounded | The plan's full list of proposed changes (its Scope/Changes section, in-scope and not-in-scope lines), read end to end. | Pass if every listed change is necessary to fix the named bug, and anything extra the plan considered is explicitly named as deferred/out-of-scope with a reason, not built. Fail if the plan bundles unrelated rewrites, migrations, new features, new config/options, or a redesign alongside the core fix — "while I'm in there" work the issue never asked for. An honest, reasoned deferral of extra work (scoping down) is the opposite of this failure and must not be graded against it. | required |
| Executable | The plan's stated files/functions/areas and its approach or order of work. | Pass if a specific file or module is named and the approach/mechanism is decided, even if the exact function or line is left to be pinned down while tracing — provided the plan shows a concrete way to find it (e.g., already-working debug output, a named code path) rather than a plan to go figure out which layer is even responsible. Fail if the approach itself is undecided — language like "somewhere," "maybe," "whichever is easier," an unresolved choice between layers/libraries/approaches, or no files/modules named at all. | required |
| Decisive test plan | The plan's test plan, read against the repro evidence's steps and the specific observable behavior the bug produces. | Pass if the test plan names a concrete, observable outcome tied to the actual bug behavior — typically the repro steps re-run with a stated expected change (e.g., "the color flips without leaving the view," "the control and the buggy case now match"). Fail if the test plan is a feeling ("should feel faster"), a generic process with no fix-specific outcome named ("run the full test suite"), or absent. | required |
| Thread & convention comms | The plan comment, read against the thread highlights (for any explicit maintainer/owner direction already given) and the repo-facts block (for the stated contribution policy, including any AI-use disclosure requirement). | Pass if the comment does not contradict or ignore explicit direction already given in the thread, AND discloses AI assistance if the repo's stated policy requires disclosure (every package here is treated as AI-assisted work, so a required-disclosure repo with no disclosure fails regardless of how good the plan is). Fail if either condition is violated. | required |

## Verdict rule

Accept only if all five required checks pass. A fail on any single required check holds the package, no matter how strong the others are — these checks are independent traps, and a plan that is grounded, bounded, executable, and decisively testable can still hold on comms alone, and vice versa. There are no preferred checks this week; nothing here is for ranking, there is exactly one plan to grade.

`unclear` on any required check counts as a fail for that check (and therefore forces reject): a plan whose grounding, scope, executability, test plan, or comms this package cannot verify is not ready to post and build from.
